# Addendum: Open Vocabulary, Human-Like Constraints

This is a follow-up to the original spec (`orchard_language_emergence_spec.md`). It replaces the communication-channel design in Section 2.2 and adds a new mechanism to Section 4. Everything else in the original spec (world design, economy, agent decision heads, population/generations, metrics, logging) stays as-is. Read the original spec first; this document only describes what changes and why.

## Why this change

The original design used a small fixed set of meaningless tokens (20-40 total) as the bottleneck that forces compression and compositionality. That produces something more like a code than a language — it can't have "more words," longer variable sentences, or anything resembling vocabulary growth, because the vocabulary is fixed and tiny by construction.

The goal now is closer to how human language actually works: an open-ended vocabulary built from a small set of atomic sub-word symbols, sentences of variable and potentially substantial length, but still governed by *human* cognitive constraints rather than unlimited machine bandwidth. Note that these agents are text/symbol-based, not speech-based — there is no need for a spoken-letter alphabet (no "a-z"), since nothing here is pronounced. What's needed instead is a small fixed inventory of **meaningless atomic tokens** that play the structural role phonemes play in human language: a small closed set that gets combined into an open-ended vocabulary of "words." Critically, the human constraints we want are not arbitrary hard caps — they are pressures that in real languages produce exactly the outcomes described below (short, frequent, irregular words for common concepts; longer, rarer, more regular/compositional words for uncommon concepts; loss of obscure forms over generational transmission). Implement them as pressures/costs in the model, not as hardcoded rules about what words are allowed to look like — the goal is for these properties to emerge under pressure, the same way compositionality itself is supposed to emerge, not to be hand-designed in.

## 1. Replace the communication channel (supersedes original Section 2.2)

- **Atomic token inventory**: a small fixed set of meaningless atomic tokens (e.g. 30-50 total, tune as needed), playing the role a phoneme inventory plays in human language. These are just integer ids into an embedding table at the start — no pre-assigned meaning, same principle as the original spec's Section 2.2 (do not hand-design any token's meaning).
- **Words are formed by hyphenating atomic tokens together**: a "word" is one atomic token on its own, or a chain of atomic tokens joined by a hyphen symbol (e.g. `tok7-tok22-tok3` is a single three-token word). The hyphen is a structural symbol emitted by the agent, not a separate meaningful token — it just marks "these atomic tokens belong to the same word." There is no fixed cap on how many atomic tokens can be hyphenated into one word other than the overall message-length cap below; short common words will typically be one or a few tokens, and the model should be free to build longer words when useful.
- **Words are separated by a space symbol**: a "sentence" (one turn's message) is one or more words separated by a space symbol. The space, like the hyphen, is a structural symbol, not a meaningful token itself.
- **Generation is autoregressive over this symbol stream**: the agent's message-output head predicts one symbol at a time — where each step's symbol is either an atomic token, a hyphen, or a space — continuing until it emits an end-of-message symbol or hits the max length cap. This is a small sequence model over a mixed vocabulary of {atomic tokens} ∪ {hyphen, space, end-of-message}, not single fixed-token selection — this is the main architectural change from the original spec, and it will need a different training loop for the message head (see Section 4 on training implications). It is simpler than full character-level generation (fewer possible symbols per step than 26+ letters) but still a genuine sequence-generation problem, not one-shot token selection.
- **Per-turn max length**: a soft cap on total symbols emitted per turn (counting atomic tokens, hyphens, and spaces together) — generous enough to allow multi-word phrases, not so generous that agents can encode a whole scenario as one long opaque blob with no internal structure. Start on the smaller end and relax once training is validated (see Section 4).
- **Turn limit**: keep this from the original spec (6-10 alternating turns per negotiation) — this cap is independent of vocabulary and still matters for the same reasons.
- **Do not hand-segment "words" beyond the structural hyphen/space markers described above.** The agent decides where to place hyphens and spaces itself; the implementer does not impose word boundaries beyond providing these two structural symbols for the agent to use. If and how consistently agents actually use hyphens to build multi-token words, versus falling back on single-token words, is something to detect via analysis (Section 3 below), not something to force.

## 2. Pressures that produce human-like vocabulary properties (new mechanisms)

None of these are hard rules about what an agent is allowed to say. They are costs/pressures added to the RL objective and to the transmission bottleneck, designed so that the same kind of outcome humans ended up with (short common words, longer rare words, loss of obscure irregular forms over time) is what a rational reward-maximizing agent, or a memory-limited newborn learner, will actually converge toward.

### 2.1 Length cost (produces "no absurdly long sentences")
Add a small negative reward proportional to message length (total symbols used — atomic tokens, hyphens, and spaces all count) per turn, on top of the existing turn-limit cap. This gives a *soft* pressure toward brevity in addition to the *hard* cap, which better matches the human situation (people usually don't max out the longest sentence they could physically produce; long sentences are costly to produce and to parse, not simply forbidden). Tune the cost coefficient so it discourages padding/babbling without preventing genuinely useful longer utterances when the task calls for one (e.g., naming a more complex meaning that actually requires more information).

### 2.2 Frequency-linked cost, to produce Zipfian-style economy (produces "common concepts get short words")
This is the mechanism most directly responsible for the human pattern where frequent words tend to be short (a well-known property of natural language, related to Zipf's law and to information-theoretic accounts of word length): give agents a (small) incentive to reuse shorter token-sequences for concepts/meanings that come up often in the world, by making the length-cost in 2.1 apply per-episode as normal — since frequent meanings will be negotiated far more often than rare ones over the course of training, the cumulative RL pressure to shorten will naturally act more strongly on whatever token-sequences end up encoding frequent meanings, purely because those code-length costs are paid far more often. You do not need a separate explicit frequency-tracking reward term for this — it should emerge from the interaction between message-length cost and the natural frequency distribution of meanings in the world (make sure the world's meaning-distribution is itself somewhat skewed — e.g., some varieties/quantities/price-ranges should occur much more often than others — or this pressure has nothing to act on). Log meaning-frequency alongside message-length-per-meaning specifically so you can check afterward whether this correlation actually emerged (this is a testable, fully-instrumentable prediction, not just a hoped-for side effect).

### 2.3 Memory/capacity limit on newborns (produces "no broadly-useless overly-specific words," and is the main lever for #2.4 below)
When a newborn agent goes through the transmission-bottleneck supervised-pretraining phase (original spec Section 4), impose an explicit **capacity limit** on what it can absorb: instead of (or in addition to) simply limiting the *number* of sampled transcripts it trains on, limit the newborn's ability to fit rare, idiosyncratic patterns by ensuring the sample it learns from is dominated by frequent-meaning examples with only a light sprinkling of rare ones (i.e., sample transcripts to imitate roughly proportional to how often each meaning-type actually occurred in the parent generation, not uniformly across all meaning-types) — this means a newborn will see many examples of common trades and few or zero examples of rare/unusual ones, so it will reliably generalize a systematic pattern for common cases but will often fail to reproduce whatever narrow, possibly-irregular form a rare case happened to acquire. This directly produces vocabulary loss / regularization of rare forms over generations (see 2.4) as a natural consequence of limited sample exposure, rather than needing a separate "forgetting" mechanism.

### 2.4 Generational drift / loss of obscure forms (the historical-linguistics analogy you asked for)
This should not be implemented as an extra bespoke mechanism — it should fall out of 2.3 plus ordinary population turnover (original spec Section 3), and your job is mainly to **instrument and verify** that it's happening, since it's a prediction, not a guarranteed outcome:
- Track, per specific "meaning" (a specific variety+quantity+quality+price-range combination), the message(s) used to express it, generation over generation.
- Rare meanings should show higher **volatility** across generations (the message used for that meaning changes, drifts, or gets replaced by a more generic/compositional construction) compared to frequent meanings, which should be comparatively stable once converged.
- Specifically watch for and log: cases where an early generation develops a short, possibly-irregular/idiosyncratic message for some meaning that happened to be common *at that time*, but as world dynamics or population composition shift which meanings are actually frequent, later generations fail to inherit that specific form (because 2.3 means newborns rarely if ever saw it) and instead reconstruct that meaning compositionally from more general, more frequently-reinforced building blocks. That reconstruction-from-general-parts-when-the-specific-form-is-lost is the direct analogy to historical regularization (e.g., irregular verb forms leveling out to the regular pattern over generations of language transmission) and is worth specifically calling out in the final report if observed.
- This means your metrics (original spec Section 5) should be computed **per meaning-frequency-bucket** (frequent vs. rare meanings), not just globally averaged — a global-average compositionality or stability score can hide exactly this effect (frequent meanings being stable/short/possibly-irregular, rare meanings being volatile/longer/compositional), so bucket the analysis or you won't be able to see the pattern even if it occurs.

## 3. New analysis requirements (in addition to original Section 5)

Add to the metrics/analysis suite:
1. **Length-frequency correlation**: correlation between how often a meaning occurs and the length (in symbols, and separately in word-count) of the message used to express it. Predicted: negative correlation (frequent meanings -> shorter messages) if 2.2 worked as intended. Report this explicitly, don't just eyeball it.
2. **Word-like unit detection**: segment each message into "words" using the agent's own space symbol (this segmentation is trivial and given for free by the space symbol — no substring-mining needed, unlike a character-level channel). For each word, also record its internal hyphenated token structure. Treat these as the units for vocabulary analysis: word frequency distribution, word length distribution (in atomic tokens), and reuse of specific hyphenated token-sequences across different messages/meanings.
3. **Per-bucket (frequent vs. rare meaning) stability and compositionality scores**, per 2.4 above.
4. **Generational form-survival tracking**: for a sample of specific meanings, track whether the word (or multi-word phrase) used for that meaning survives, drifts, or is replaced by a compositionally-reconstructed alternative across generational turnover, and report specific before/after examples of this in the final report if found (these will be some of the most human-readable, interesting output of the whole project — prioritize surfacing them clearly).

## 4. Training implications and things to watch for

- Autoregressive generation over the {atomic tokens, hyphen, space, end-of-message} symbol stream is a materially harder RL problem than single fixed-token selection (original spec's simpler channel) — expect slower convergence and more instability, though it should be somewhat easier than full character-level generation since the per-step symbol vocabulary is smaller (30-50 atomic tokens plus 3 structural symbols, vs. 26+ letters, and words tend to need far fewer tokens than letters to spell the same message). If REINFORCE proves too noisy, consider: (a) a length-capped setting on the smaller end first (e.g., start prototyping with a low max-symbols-per-turn cap, then relax it once training is stable), or (b) Gumbel-softmax relaxation through the symbol sequence during training if the implementer is comfortable with it, or (c) pretraining the generation head with a brief "babbling" phase against a simple self-consistency or auto-encoding objective before RL begins, purely to get past the cold-start problem of random symbol output being essentially never useful early on (this is not language pretraining on real text — it would just be the agent learning to produce *any* stable self-consistent symbol patterns, including reasonable use of the hyphen/space structural symbols, before those patterns are shaped by trade outcomes; if this is done, document it clearly as a technical bootstrapping step, not a source of linguistic content).
- **Watch explicitly for degenerate long babbling** (agents maxing out the length cap with unstructured noise that happens to correlate with outcomes via brute-force memorization) — this is the most likely new failure mode introduced by removing the small fixed vocabulary. The length-cost pressure (2.1) is your main defense; if it isn't sufficient, tightening the max-length cap further is a reasonable fallback even though it's less "human-like" — a broken run that trivially fails is worse than a somewhat tighter cap.
- **Watch for degenerate hyphen/space usage** specifically: e.g., agents never using the hyphen at all (falling back to single-token words exclusively — acceptable, but worth noting since it means multi-token "words" never emerged), or using the hyphen/space essentially randomly with no consistent word-like structure (a sign the sequence-generation training hasn't converged rather than a sign of anything linguistically interesting). Distinguish these explicitly in the final report rather than treating any hyphen/space usage as evidence of word formation.
- Re-run the build-order comparison from the original spec's Section 7, step 6 (bottleneck on vs. off) under this new channel design as well — the transmission bottleneck (now doing more work than before, see the intro to this addendum) is even more important to verify is actually contributing, not just assumed to be.

## 5. Config additions

Add to the existing config system (original spec Section 8): atomic-token-inventory-size (e.g. 30-50), max-message-length-in-symbols, length-cost-coefficient, newborn-sample-frequency-skew (how strongly the transmission-bottleneck sample favors frequent over rare meanings — this directly controls how aggressively 2.3/2.4 operate, so it should be an easily tunable parameter, not hardcoded).
